# Balletmaster Observability — архитектурный эскиз

> **Статус:** Draft / для обсуждения, не утверждённое ТЗ  
> **Версия:** 0.3  
> **Дата:** 2026-11-12  
> **Контрольная версия репозитория:** `475651597b702a0f7e5f6acec79087e68a24bc22` (`main`)  
> **Назначение:** зафиксировать текущее состояние, согласованные направления, варианты архитектуры и границы ближайших задач. Документ предназначен в том числе для чтения Antigravity.

## История изменений

- **v0.1:** первая карта направлений Observability, компонентов и границ реализации.
- **v0.2:** учтено архитектурное ревью: production-полнота событий, альтернативные пути телеметрии, корреляция конкурирующих исполнений, ограничения сверки с Store, контроль стоимости Query и конкретные диагностические сценарии. **Ни один из открытых вопросов не объявлен решённым автоматически.**

Новые решения о реализации **не принимались**.

## 1. Зачем нужен этот документ

Balletmaster — встраиваемый Kotlin/JVM SDK для исполнения цепочек шагов, Replay, идемпотентности, работы с lease и сохранения фактов исполнения через `Store`. Системное логирование уже реализовано. Следующая цель — не просто отправлять логи во внешнее хранилище, но использовать их для **исследования конкретных операций, мониторинга большого количества процессов, потокового анализа и реакций**.

Пример целевого контекста: банковский middleware, где Balletmaster координирует большое количество относительно простых операций с вызовами antifraud, payment gateway и АБС, обратными событиями и ветвлениями обработки ошибок. Высокий поток операций сам по себе не делает систему Big Data, но предъявляет требования к стоимости и надёжности наблюдаемости.

**Важное ограничение:** это архитектурный эскиз. Он **не разрешает Antigravity самостоятельно создавать новые модули, менять ядро или реализовывать всю подсистему**. Каждая реализация требует отдельной согласованной задачи и небольшого ревьюируемого изменения.

## 2. Статусы решений

- **Реализовано** — подтверждено исходниками текущего репозитория.
- **Согласованное направление** — принцип, выбранный в обсуждении; детали ещё могут уточняться.
- **Рабочая гипотеза** — разумный вариант для изучения, но не окончательное решение.
- **Открытый вопрос** — решение ещё предстоит принять.

## 3. Текущее состояние (реализовано)

1. Репозиторий уже использует **multi-module Maven**: корневой `pom.xml` — `packaging=pom`, код размещён в модуле `core/`; других модулей пока нет. Существующие Maven-координаты — `org.example:ballet-master:1.0-SNAPSHOT`, артефакт модуля — `core`. Предлагаемые ниже имена модулей пока условные.
2. В `core` находятся `Step`, `ContextImpl`, `CallContextManager`, `Try`, API `Store`, `InMemoryStore`, Replay, Lease, StateConfig и `ProcessSupervisor`.
3. Системное логирование использует **SLF4J 2.0 Fluent API** (`addKeyValue`) и MDC; backend и формат вывода настраивает приложение-хост. **Сам SDK не гарантирует JSON в выходном потоке.**
4. Есть категории `step`, `lock`, `replay`, `store`, `state`, фиксированный каталог событий и корреляционные поля `ballet.operation`, `ballet.operationId`, `ballet.attempt`, `ballet.suffix`, `ballet.step`, `ballet.replay`.
5. Основные события жизненного цикла (`step.started`, `step.completed`, `chain.stopped`) сейчас **DEBUG**; события блокировок частично TRACE, аномалии — WARN/ERROR. **Из логов уровня INFO нельзя рассчитывать восстановить полную историю шагов.**
6. Нет реализации чтения из Loki/облаков, потоковых адаптеров, готовых облачных правил мониторинга, Investigation Engine и Reaction Runtime.
7. `CallContextManager` и MDC используют контекст текущего потока (`ThreadLocal`/SLF4J MDC); автоматический перенос контекста на другой поток или в coroutine/async execution не гарантирован.
8. Текущий `Store` предоставляет точечные операции `get`/`set`/`inc` и CAS-подобный условный `set`, но не предоставляет API перечисления шагов, попыток, суффиксов или истории операции. Ключи исполнения формируются внутри `ContextImpl`. Чтение persisted output может потребовать доменных классов приложения. Существующий `ProcessSupervisor` может вычислить состояние по `StateConfig`, не отдавая пользовательские payload'ы, но требует классы доменной модели (`Class<S>` и `Class<STATE>`) и проверяет факты для **конкретных** `attempt` и `suffix`. Он не является универсальным API инспекции истории.
9. `step.exception` намеренно раскрывает только имя класса исключения. Сообщение, stack trace и причинная связь с внешним API могут быть доступны лишь в логах/трассировках хоста при условии корректной корреляции.

**Нормативный источник для существующего логирования:** [`docs/logging.md`](logging.md). Если этот документ и `logging.md` расходятся в описании **уже реализованного** поведения, первичны исходный код и `logging.md`; расхождение необходимо вынести на обсуждение, а не молча «исправить».

## 4. Цель и нецели Observability

**Цели:**

- Найти и интерпретировать системные события конкретного экземпляра операции в заданном временном диапазоне.
- Использовать возможности внешних платформ для агрегирования, правил и алертов без переписывания их внутри Balletmaster.
- При высокой нагрузке передавать наблюдения в потоковый анализ с корреляцией событий, окнами и обнаружением аномалий последовательности.
- Передавать результаты анализа в пользовательский код: webhook, callback, функцию или отдельный сервис — без требования к конкретной среде исполнения.
- Поддерживать разные провайдеры (Loki/Grafana, AWS, Azure, GCP) независимыми интеграционными артефактами.

**Нецели ближайшего этапа:**

- Создание собственного универсального логового хранилища, брокера сообщений или аналога Grafana.
- Обязательный отдельный JVM-сервис для каждого адаптера.
- Универсальный компилятор правил между LogQL/KQL/CloudWatch/GCP.
- Сложный процессный CEP-движок или автоматическая компенсация бизнес-операций на основании логов в первом MVP.
- Переделка уже очищенного ядра ради Observability до появления подтверждённой потребности.

## 5. Принципы и согласованные направления

**5.1. Источник истины.** `Store` хранит авторитетные факты исполнения. Логи — наблюдения: они могут задерживаться, теряться, дублироваться, быть отключены настройкой уровня или не попасть в доступное окно retention. Отсутствие записи не доказывает отсутствие действия. Решение об изменении бизнес-состояния, Replay или компенсации не принимается только по логам.

**5.2. Независимые способы потребления.** Historical Query, Native Monitoring, Streaming Analysis и Investigation/Reaction — разные контуры, а не обязательные стадии одного конвейера.

**5.3. Изоляция приложения.** Сбор, экспорт, запросы и обработка не должны блокировать обычный путь выполнения Step или заметно увеличивать его задержку. Стоимость наблюдаемости при высокой нагрузке — явный архитектурный критерий.

**5.4. Модули — по технологиям и ответственности.** Интеграция с конкретным сервисом — отдельный артефакт. Общие контракты могут существовать отдельно, но не следует создавать «абстракцию ради абстракции». Не каждый артефакт обязан быть JAR: конфигурации, правила и примеры развёртывания также являются поставляемыми компонентами.

**5.5. Размещение не предписано библиотекой.** Клиент запросов к логам должен быть переиспользуемой библиотекой. Его вызывающая среда может быть JVM-приложением, CLI, Kubernetes Job, Spring-сервисом, Lambda/Function и т. п. Нужна отдельная причина, чтобы создавать постоянно работающий процесс.

### 5.6. Production-события — блокирующий архитектурный вопрос

Существующий профиль `INFO` **не обеспечивает полную наблюдаемость жизненного цикла**. На `INFO` доступны лишь выбранные `INFO`/`WARN`/`ERROR` события, а `step.started`, `step.completed`, `chain.stopped`, штатные пропуски и обычные бизнес-исключения (DEBUG) отсутствуют. Это не дефект текущего System Logging: он проектировался как малошумная диагностика. Но **полноценный Streaming / process-aware monitoring на базе этих логов при стандартной конфигурации невозможен**.

До production-дизайна нужно выбрать и измерить одну или комбинацию стратегий:

1. **Event-level policy:** повысить доступность ограниченного набора действительно значимых исходов, сохранив различие ожидаемых `SKIP`/`BLOCKED` и ошибок. Без автоматического перевода всех остановок в WARN.
2. **Conditional/targeted diagnostics:** выборочно включать подробные события для операций, категорий, временных интервалов или при аномалии; оценить реальные возможности и стоимость буферизации/сэмплирования.
3. **Direct telemetry/metric hook (вариант):** разрешить независимый от SLF4J путь записи ограниченного набора наблюдений/агрегатов, например для метрик, OTel и потоковой доставки. Нужно отдельно спроектировать стоимость, ошибкоизоляцию и контракт, не навязав брокер или OTel в Core.
4. **Collector-derived metrics:** сохранять схему SLF4J → collector → внешняя система, если нужные события доступны и цена приемлема.

Это **варианты, не выбранная реализация**. Не следует одновременно менять logging levels, добавлять новый SPI и строить собственный метрик-движок. Минимальная экспертиза: определить 3–5 целевых сигналов, нужные события, допустимую потерю/задержку и ориентировочный бюджет событий/CPU/ingestion при целевой нагрузке. Результат — явный *Production Telemetry Profile* или решение о необходимости hook.

### 5.7. Отдельная граница: диагностические наблюдения и авторитетные факты

Системные события могут дать оператору гипотезу о гонке, застрявшем шаге или потере результата. Они **не подтверждают**, что бизнес-действие выполнено или не выполнено. Условие «нет `step.completed`» может означать падение процесса, выключенный DEBUG, задержку/потерю доставки, выход за временной диапазон либо реальный незавершённый шаг. Любая управляющая реакция требует дополнительных достоверных данных.

## 6. Четыре контура Observability

### A. Historical Query / Manual Investigation

**Триггер:** запрос оператора, службы поддержки или внешнего API.  
**Функция:** найти события операции за период, нормализовать и представить **доступную хронологию наблюдений**; затем, при необходимости, проанализировать её. Сортировка по времени не гарантирует строгий причинно-следственный порядок между инстансами.  
**Возможная реализация:** Query Adapter к Loki, CloudWatch Logs, Azure Monitor Logs либо Google Cloud Logging.  
**Выход:** события, сведения о полноте/ограничениях выборки, ссылки на исходные записи; в дальнейшем — диагностический отчёт.

**Обоснование собственного клиента:** программная композиция нескольких диагностических запросов, запросы из backend/support API и повторное использование нормализованных наблюдений в Investigation. **Наличие Grafana UI само по себе не является причиной писать свой CLI.** Для первого эксперимента достаточно CLI как тестового runtime; ценность публичной библиотеки должна подтверждаться конкретным use case. Исторический query **не является гарантией полноты** даже при успешном HTTP-ответе.

### B. Native Monitoring & Alerting

**Триггер:** правила, вычисляемые средствами внешней платформы.  
**Функция:** агрегаты, пороги, частоты ошибок, показатели задержки, уведомления.  
**Возможная поставка:** пакеты LogQL-правил/Grafana provisioning, CloudWatch alarms/filters, Azure Monitor KQL alerts, Google Cloud log-based metrics/alert policies.  
**Выход:** алерт или сигнал во внешнюю систему; при необходимости — вызов нашего Investigation/Reaction.

Важно: платформа обычно исполняет **свой язык запросов и правила**, а не произвольный Kotlin-код Balletmaster. Прикладной код запускается во внешнем runtime через соответствующий механизм интеграции.

### C. Streaming Observation / Process-aware Analysis

**Триггер:** входящий поток событий.  
**Функция:** корреляция большого числа процессов, временные окна, обработка опоздавших и повторных записей, обнаружение проблемных последовательностей.  
**Варианты доставки:** ответвление потока в collector/agent **до** хранилища логов или штатный экспорт/подписка **из** облачной платформы; далее Kafka, Kinesis, Event Hubs, Pub/Sub либо иной транспорт.  
**Выход:** findings, агрегированные метрики и сигналы Reaction/Investigation.

Для высоконагруженного применения нужно рассмотреть **не только** парсинг сериализованных SLF4J-строк, но и прямой telemetry/event hook из Core (см. п. 5.6). Оба варианта могут иметь независимую ценность: текстовые логи для диагностики человека, поток структурированных фактов наблюдения — для аналитики. *Ни один путь сейчас не принят*. Нельзя принимать WebSocket `tail` за надёжный поток с подтверждением обработки.

**Не считать Loki `tail` полноценным надёжным брокером событий.** Он полезен для интерактивного near-real-time наблюдения, но не заменяет гарантированную доставку, checkpoints и replay. Потоковый анализ не обязан получать события через исторический Query API.

### D. Investigation & Reaction

**Триггер:** ручной запрос, native alert или результат потокового анализа.  
**Функция:** обобщить наблюдения, сформировать обоснованные диагностические выводы, при необходимости сверить гипотезу с `Store`; передать результат пользовательскому обработчику.  
**Выход:** `Finding`/`InvestigationReport` с доказательствами, степенью уверенности, ограничениями данных; callback/webhook/notification.  
**Граница:** факт получения алерта — ещё не разрешение изменять бизнес-процесс. Автоматические управляющие действия требуют отдельного подтверждённого дизайна и проверки Store.

**Ограничение текущей реализации:** непосредственная сверка с Store по произвольному `operationId` из внешнего runtime пока **не поддерживается публичным inspection API**. `ProcessSupervisor` уже умеет интерпретировать сохранённые факты в бизнес-состояние, но только при наличии `StateConfig` и доменных классов хоста и для заданных `attempt`/`suffix`; это не поиск всех исполнений или шагов операции. Возможный вариант — опциональный read-only endpoint/callback на стороне хост-приложения, который возвращает ограниченный агрегированный статус, не передавая payload'ы внешнему анализатору. Альтернативы (специальный Core inspection API или иная модель доступа) остаются открытыми. До принятия решения не обещать универсальную `Store Enrichment` функцию.

## 7. Логические потоки данных

```text
                        Host Application + Balletmaster Core
                                       |
                                  SLF4J events
                                       |
                         Logging backend / Collector
                                  /          \
                                 /            \
                      Log platform          Event transport
                  Loki / cloud logs       Kafka / cloud streams
                       |      |                  |
             Historical Query  Native rules    Stream Analysis
                       |      |                  |
                       |    Alert/Signal      Finding
                       \       |                /
                        \      |               /
                     Investigation / Reaction
                               |
                         Host integration
```

**Разветвление после Collector — вариант, а не обязательная топология.** В AWS, Azure и GCP поток можно организовать через соответствующие подписки/экспорт логов. Путь, latency и гарантии доставки нужно выбирать отдельно для провайдера.

**Альтернативная топология — гипотеза, требующая сравнения:**

```text
                   Balletmaster Core
                    /            \
              SLF4J logs       Optional telemetry hook (not implemented)
                  |                         |
            Logging backend            Metric/OTel/stream adapter
                  |                         |
             Log platform               Metric / Stream platform
```

Схема не означает внедрения hook. Цель — не зафиксировать единственный путь данных раньше, чем определены потребности в production, объём потока и требования к доставке.

## 8. Карта возможных компонентов и поставок

| Логический компонент | Ответственность | Тип поставки | Статус |
|---|---|---|---|
| `core` | Исполнение и публикация системных событий | JVM JAR | Реализовано |
| Observation/Event Model | Нормализованный контракт событий, корреляция, provenance | JVM library / schema | Рабочая гипотеза |
| Query API | Запрос исторических событий, лимиты и полнота выборки; общность разных провайдеров пока не доказана | Возможно JVM library, возможно provider-specific | Рабочая гипотеза |
| Loki Query Adapter | LogQL / Loki HTTP API, декодирование ответа | JVM JAR | Кандидат первого адаптера |
| Cloud Query Adapters | CloudWatch / Azure Monitor / GCP Logging | Отдельный JAR на сервис | Позже |
| Native Rule Packs | Запросы и правила алертов для каждой платформы | YAML/JSON/конфигурации | Отдельная ветка |
| Stream Ingestion Adapters | Приём из Kafka/Kinesis/Event Hubs/PubSub | Отдельные JAR/runtime-адаптеры | Позже |
| Optional Telemetry Sink / Metrics SPI | Возможный независимый от логов путь передачи ограниченных наблюдений | Контракт в Core + внешние адаптеры, **только если выбран** | Открытый вопрос |
| Stream Analysis | Корреляция по времени и состоянию множества операций | JVM library + runtime | Позже |
| Investigation Engine | Правила диагностики и отчёт с evidence | JVM library | После проверки Query |
| Reaction Integration | Передача finding/alert в код хоста | library/webhook/function integration | Позже |
| Example Runtime | Интеграционный proof-of-concept, CLI или job | Исполняемый example | Для вертикального MVP |

Названия условны; **не создавать все артефакты заранее**. Предпочтительная форма: маленькие модули без навязанных зависимостей на Spring, облачный runtime или конкретное хранилище, если эти зависимости не нужны для их ответственности.

## 9. Вопросы к общему контракту событий (пока НЕ утверждённый API)

Для нескольких независимых провайдеров и механизмов обработки, вероятно, понадобится модель **нормализованного системного события**. Минимальные категории данных для обсуждения:

- Время события (и при необходимости время приёма), тип события, severity, источник/категория. **Временная отметка не задаёт глобального порядка**: clock skew между нодами, буферизация и задержки доставки могут переставлять события. Даже общий `executionId` сам по себе не гарантирует последовательность при асинхронной работе; для строгого порядка в пределах определённой области понадобятся подтверждённые гарантии источника, локальный sequence или причинные связи. Не выводить causal ordering только из сортировки по timestamp.
- Корреляция: имя/ID операции, попытка, step, suffix, replay и контекст среды исполнения — если они присутствовали в исходном сообщении.
- **Параллельные запуски одной операции:** текущей связки `operationId` + `attempt` + `suffix` + `step` недостаточно, чтобы строго отличить два воркера, обрабатывающих одну и ту же доставку/попытку. Рассмотреть `executionId`/`invocationId` отдельно от идентификатора бизнес-операции. Сначала определить границу жизни идентификатора (вызов цепочки? шаг? входящее сообщение?) и генератора/владельца, затем оценить стоимость и совместимость. `pod`, `thread`, `traceId` могут помочь, но не являются универсальным эквивалентом идентификатора исполнения.
- Типизированные атрибуты события и совместимость с существующим каталогом `docs/logging.md`.
- Происхождение: провайдер, координаты/ссылка на исходный лог, отметки парсинга.
- Неопределённость: отсутствующие поля, повреждённые сообщения, частичная выборка.

**Текущий Core не публикует обязательные `eventId` и `schemaVersion`**. Их необходимость, способ введения и стоимость при высокой нагрузке — открытые вопросы; нельзя представлять их как уже существующие поля. `EventSource` для исторического поиска и интерфейс потокового подписчика, вероятно, должны быть **разными контрактами**: у них разные ограничения по completeness, задержкам, backpressure, ack и checkpoints.

**Не фиксировать универсальный query-клиент заранее.** Для CloudWatch Logs Insights `StartQuery`/`GetQueryResults` — серверная операция с отслеживанием статуса; Loki возвращает range-results с собственными лимитами; Azure Monitor Logs имеет прямой Query API; Google Cloud Logging — `entries.list` с `pageToken`. Общей может оказаться лишь модель нормализованного события и сведений о полноте, а не единая транспортная семантика или сигнатура метода. `async` в имени SDK-метода не обязательно означает серверную job-модель.

## 10. Нефункциональные требования к будущим интеграциям

- **Completeness и порядок:** пагинация, серверные лимиты, retention, выбор диапазона и границы времени; явное различение «данных нет» и «выборка неполна/недоступна». События из разных воркеров могут иметь несогласованные часы и приходить не по порядку: timestamp задаёт приблизительную хронологию, а не глобальное `happens-before`. Сама принадлежность одному `executionId` не гарантирует последовательность.
- **Streaming semantics:** возможные дубли, out-of-order, late arrival, retry, delivery gaps, backpressure, checkpoints; требования определяются транспортом, не обещать exactly-once по умолчанию.
- **Isolation:** сбой внешней платформы наблюдаемости не должен останавливать `core`.
- **Security:** read-only credentials для query-адаптеров, разграничение tenant/operation access, отсутствие секретов в URL/логах, ограничение объёма извлекаемых данных. **Текущий Core не гарантирует redaction**: имена и идентификаторы операций, suffix, Store key и сообщения некоторых инфраструктурных исключений могут содержать чувствительную информацию. Ответственность за их состав — у хоста; masking/redaction на logging backend/collector — отдельный policy, не следует приписывать его SDK. Потребление логов внешним анализатором также требует собственной авторизации и data minimization.
- **Cardinality & cost:** имя `operation` может быть low-cardinality **только при ограниченном справочнике**; `operationId` обычно high-cardinality и не должен становиться индексируемым Loki label. Для Loki предпочитать статические селекторы `app`/`environment`/`namespace`/`tenant` (если применимо), затем фильтры по structured metadata/JSON или содержимому записи. Контролировать sampling, logging level, ingestion и расходы на запросы.
- **Query budget:** ограничивать диапазон времени, логовые источники, общий объём возвращаемых записей, число подзапросов, длительность, повторные попытки и отмену; явно сообщать о truncation, timeout, partial results и неизвестной полноте. Не обещать, что удачный поиск по `operationId` при высокой нагрузке будет дешёвым без измерений.
- **Execution correlation:** обеспечить различение конкурирующих исполнений одного `operationId`, если диагностика гонок входит в требования. Не принимать сочетание `operationId + attempt + step` за уникальный ключ физического запуска.
- **Отдельный риск Core, не задача Observability:** текущая lease-логика использует локальные часы воркера (`System.currentTimeMillis()`). Clock skew может влиять не только на восстановление истории, но и на корректность решения об истечении аренды; оценивать отдельно при проектировании распределённых Store и lease, не исправлять в рамках данного документа.
- **Compatibility:** формат событий реально зависит от backend-конфигурации. Требуются пример JSON/structured pipeline и тесты, что SLF4J key-value attributes не потеряны.
- **Observability of Observability:** ошибки парсинга, задержки поступления, пропуски, lag, rate limits, стоимость запросов и сбои доставки должны быть диагностируемы.

## 11. Вертикальные срезы — кандидаты, выбор не сделан

**Статус: рабочие гипотезы.** На Шаге 0а выбирается **один** первый эксперимент из трёх независимых контуров. Ни Loki Query, ни Native Alerting, ни Streaming пока не утверждены приоритетом. Выбор должен опираться на конкретный пользовательский сценарий, доступность данных, измеримую ценность и стоимость проверки, а не на удобство реализации выбранного адаптера.

### 11.1. Кандидат A — Historical Query через Loki

**Экспериментальный путь:** `core → JSON-совместимый logging backend/collector → Loki → Kotlin Query Adapter → консольный результат`.

Такой срез проверяет чтение реальных структурированных событий Balletmaster из внешней платформы и их получение в коде без постоянно работающего сервиса. Он **не доказывает** пригодность стандартного INFO-профиля для production Monitoring/Streaming: при испытании необходимых lifecycle-событий потребуется явно включить соответствующий уровень (например, DEBUG).

**Критерии эксперимента (если выбран именно он):**

1. Хост генерирует реальные события Balletmaster с корректной корреляцией, не теряя `addKeyValue` при сериализации.
2. События доступны в Loki; документированы labels, фильтры, ограничение окружения/приложения/tenant и окна времени. `operationId` не используется как высококардинальная индексируемая метка. Оценена стоимость поиска на тестовом объёме.
3. Kotlin-клиент возвращает наблюдения одной операции за ограниченный интервал вместе с provenance и известными ограничениями выборки.
4. Проверены пустой ответ, повреждённая запись, дубли, одинаковые timestamps, лимит ответа, timeout и недоступность Loki. Выборка не выдаётся за полную без оснований.
5. Не изменяются алгоритмы Core; Spring и отдельный постоянно работающий сервис не обязательны.

**Проверка ценности:** нужен хотя бы один сценарий, где программное чтение или интерпретация существенно полезнее обычного запроса в Grafana UI. Если его нет, можно ограничиться dashboard и native rules, не создавая Investigation-библиотеку ради неё самой.

### 11.2. Кандидат B — Native Alerting

**Экспериментальный путь:** `core → logging backend/collector → Loki/Grafana (либо выбранный облачный logging service) → native alert rule → тестовый получатель сигнала`.

**Минимальная проверка:** одно правило для реально доступного на выбранном production-уровне события, например `store.error` или `lock.stolen_expired`; подтверждение, что правило срабатывает при искусственно вызванной аномалии, не срабатывает на нормальном трафике и доставляет сигнал в тестовый endpoint. Зафиксировать стоимость/задержку правила и границы доступных полей. **Никакого собственного Stream Processor для этого среза не требуется.**

### 11.3. Кандидат C — Streaming Observation

**Экспериментальный путь (один из вариантов):** `core → logging backend/collector → event transport → минимальный consumer`. Другой вариант — поток через штатный экспорт облачной платформы; прямой telemetry hook остаётся отдельной гипотезой из п. 5.6, а не обязательным условием первого теста.

**Минимальная проверка:** получить несколько структурированных наблюдений, сохранить нужную корреляцию, воспроизвести дубликат и опоздавшее событие, обозначить правила deduplication и границы ordering. На реалистичной пробной нагрузке оценить цену сериализации/экспорта, задержку и влияние на приложение. Не использовать Loki `tail` как гарантированный транспорт. **Если требования требуют полного непрерывного потока событий, сначала согласовать Production Telemetry Profile; имеющийся INFO-профиль его не предоставляет.**

### 11.4. Эталонные диагностические сценарии (для выбора приоритета)

Это **кандидаты сценариев**, а не готовые правила с подтверждённой точностью:

1. **Неуспешная/остановленная цепочка:** различить ожидаемый `gate → SKIP`, повторную доставку (`step.skipped_idempotent`), конкурентное `BLOCKED`, бизнес-исключение и техническую ошибку `Store`. `chain.stopped` сам по себе не равен инциденту.
2. **Истёкший lease и конкурентный воркер:** сопоставить `lock.stolen_expired`, `lock.stale_unlock_skipped`, `lock.blocked` и (если внедрён) идентификатор физического исполнения. Clock skew и порядок получения логов не позволяют гарантированно восстановить причинность лишь по timestamp. Логи не доказывают отсутствие идемпотентности внешнего API или двойной платёж.
3. **Replay не продвигается к Live:** одиночный `replay.cache_miss` **нормален** для первого шага без сохранённого результата и обычно сопровождается `replay.switched_to_live`. Исследовать следует повторяющиеся попытки без прогресса, отсутствие ожидаемого перехода при достаточной полноте наблюдений или `store.error` при `original_output`; один `cache_miss` не считается аномалией.
4. **Аномальный рост ошибок по шагам:** агрегаты `store.error`, `step.exception`, `step.completed` по operation/step в ограниченном окне. Без полноценного production-потока step-событий нельзя рассчитывать долю ошибок по всем операциям.

Для каждого выбранного сценария до реализации формулируются: входные события, требования к уровню/полноте логирования, признаки подтверждения, ложноположительные случаи, latency, стоимость, необходимость Store/host API и то, чем код Balletmaster лучше имеющихся platform-native rules.

## 12. Открытые архитектурные вопросы

Ниже **десять сгруппированных вопросов**, а не десять решений. Ответы фиксируются на Шаге 0 или в последующих ADR; этот эскиз их не предрешает.

### A. Production-сигналы и стоимость

1. **Приоритет и ценность:** какой пользовательский сценарий и какой контур (Historical Query / Native Alerting / Streaming) проверяем первым? Что не покрывается существующими Grafana UI или platform-native rules?
2. **Профиль production:** какие сигналы нужны постоянно, какие — по запросу; какова требуемая полнота, задержка, допустимая потеря, объём и стоимость при высокой нагрузке? Достаточно SLF4J/log-derived metrics или нужен отдельный telemetry/metrics hook?
3. **Формат и ответственность:** что реально сериализует хост (JSON, logfmt, текст `%kvp`, OTLP и т. п.), какие свойства/поля должны сохраняться и где обеспечиваются безопасность, redaction и распространение контекста?

### B. Корреляция и модель данных

4. **Идентификаторы и порядок:** нужен ли `executionId`/`invocationId`, `eventId`, `schemaVersion`; кто владеет ими и как они связаны с `traceId`, attempt, suffix, pod/thread? Как представлять частичный порядок и clock skew, не выдавая timestamp за причинность?
5. **Общий контракт:** когда и где выделять нормализованную модель наблюдений, provenance и сведения о неполноте — в первом адаптере или в независимом модуле? Какие потребители действительно должны разделять эту модель?

### C. Запросы, провайдеры и поток

6. **Historical Query:** нужен ли единый query-контракт для разных провайдеров или достаточно общего результата при provider-specific клиентах? Читать только системные события Balletmaster или также связанные логи приложения? Как представлять лимиты, ошибки и частичную выборку?
7. **Native Monitoring:** в какой форме поставлять платформенные правила (файлы, шаблоны, chart/инфраструктурные модули, документация), и кто отвечает за их применение и lifecycle?
8. **Streaming:** какая доставка требуется для банковского сценария (дубли, lag, ordering, backpressure, retry/checkpoint, потери, replay) и на каком участке инфраструктуры лучше ветвить поток?

### D. Investigation, Store и реакции

9. **Достоверные факты:** кто предоставляет read-only сведения для проверки гипотез — хост-приложение через `ProcessSupervisor`/адаптер, будущий inspection API Core или другой механизм? Какая гранулярность требуется без раскрытия пользовательских payload'ов и при нескольких attempt/suffix?
10. **Результат и реакция:** какие findings действительно требуют нашего кода; как передавать их хосту, сохранять evidence и ограничения достоверности, не превращая логовый сигнал в самостоятельное разрешение на бизнес-действие?

## 13. Рекомендованный порядок проектирования

- **Шаг 0.** Согласовать этот эскиз как карту проблем, не как готовый design решения. Выбрать 2–3 эталонных сценария и определить требования к их production-сигналам: доступные уровни, полнота, задержка, стоимость и возможная потребность в direct hook. Core не менять до отдельного решения.
- **Шаг 0а.** Сравнить кандидатов из п. 11 и **явно выбрать** один первый вертикальный срез: Historical Query, Native Alerting или Streaming. Зафиксировать причину выбора, проверяемую гипотезу и критерии успеха.
- **Шаг 1.** Для выбранного среза составить короткий технический design note: входные события, формат экспорта, корреляция, требуемые гарантии источника, данные и план проверки. Проверить его на текущем Core.
- **Шаг 2.** Реализовать **только выбранный срез** в минимальном объёме. Если выбран Loki Query — интеграционный пример чтения; если Native Alerting — одно правило и доставка сигнала; если Streaming — один путь транспорта и минимальный consumer. Не создавать другие модули заранее.
- **Шаг 3.** По результатам эксперимента определить действительно нужные общие контракты и границы независимых артефактов. Не объявлять единый provider/query API до проверки нескольких реализаций.
- **Шаг 4.** Независимо исследовать остальные направления, опираясь на их собственные сценарии, стоимость и гарантии доставки.
- **Шаг 5.** Проектировать Investigation/Reaction тогда, когда подтверждены источники наблюдений, сценарии программной ценности и пределы сверки с авторитетными фактами.

## 14. Инструкция для Antigravity

**Это документ архитектурного контекста, а не самостоятельная задача на реализацию.** При получении поручения на Observability:

1. Прочитать этот документ, `docs/logging.md` и соответствующие исходники текущего `core`.
2. Отмечать различия между реализованным состоянием, выбранными принципами, гипотезами и открытыми вопросами.
3. Перед изменениями предлагать небольшую задачу с границами, альтернативами, рисками, тестами и минимальным diff.
4. Не создавать весь список модулей «на будущее», не менять семантику Step/Replay/Lease/Store и не строить сервис без явного запроса.
5. Сообщать о противоречиях с реальным кодом, а не самостоятельно «гармонизировать» требования.
6. Вопросы `INFO`/`DEBUG`, direct telemetry hook, `executionId` и Store inspection **не закрыты**; не реализовывать их без отдельного согласования.
7. Коммуницировать и готовить отчёты на русском языке.
